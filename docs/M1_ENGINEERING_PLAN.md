## 1. M1 目标

M1 结束时，KyStudy 应拥有一个可靠但功能极少的本地桌面基础。它不需要看起来像完整产品，但后续日程、PDF、导图、错题和 AI 都能在这个基础上演进。

M1 必须证明：

1. 应用能在 Windows 开发环境和干净测试环境中启动；
2. React 与 Rust 之间有受控、带类型的调用边界；
3. 工作区和 SQLite 可以创建、迁移、关闭并重新打开；
4. 大文件能够流式导入、去重、取消和检查完整性；
5. 数据库与 Blob 可以备份并恢复到不同目录；
6. 未授权文件、明文密钥和任意 SQL 不会暴露给前端；
7. 基础测试、格式检查和发布构建可以自动执行；
8. TV-01 至 TV-04 的技术结论有报告和 ADR 支撑。

## 2. M1 非目标

M1 不实现：

- 正式的今日页、日程编辑和统计；
- AI 真实提供商接入；
- OCR 和全文索引正式实现；
- 完整 PDF 阅读器、题目管理和复习算法；
- 思维导图编辑器；
- 多工作区切换 UI；
- 云同步、账号、自动更新和代码签名；
- 插件系统、依赖注入框架和通用事件总线。

PDF 在 M1 只做 TV-04 技术实验，用于确认坐标、性能和文件访问，不进入正式业务页面。

## 4. 实施策略

### 4.1 先验证，后固化

M1 分为两段：

1. **M1-A 技术验证**：TV-01 至 TV-04 使用最小实验消除关键不确定性；
2. **M1-B 正式基础**：根据已接受 ADR 初始化正式工程，并实现工作区、数据库、Blob 与备份。

实验代码默认可丢弃。只有接口、约束和经过测试的最小实现可以重新编写进正式工程，避免实验快捷方式成为长期架构。

### 4.2 单仓库、单桌面应用

首版只有一个桌面应用，不采用 monorepo，也不创建 `apps/desktop`、`packages/core` 等多包结构。以后确实出现第二个应用或共享包时再调整。

### 4.3 只创建正在使用的目录

工程结构表达依赖方向，但不一次创建几十个空文件、空 Service 和空 Repository。新目录必须有实际职责和测试需求。

## 5. 正式仓库结构（目标）

```text
KyStudy/
  .github/                  # CI、Issue 和 PR 模板，进入开源阶段补充
  docs/                     # PRD、数据模型、ADR、Spike 报告
  fixtures/                 # 可公开的小型生成样本与说明
  scripts/                  # 确有需要的开发和验证脚本
  src/                      # React / TypeScript 前端
    app/                    # 入口、路由、全局组合
    features/               # 按产品功能组织页面和 UI 用例客户端
    shared/                 # 通用 UI、DTO、格式化和测试工具
  src-tauri/                # Rust / Tauri 核心
    capabilities/           # 最小权限定义
    migrations/             # SQLite 迁移
    src/
      commands/             # 薄 Tauri Command
      application/          # 用例、事务和跨模块编排
      domain/               # 纯业务规则和值对象
      infrastructure/       # SQLite、Blob、备份、安全存储
      bootstrap/            # 依赖组合与启动
    tests/                  # Rust 集成测试
  tests/                    # 跨层与端到端测试，实际需要时创建
  README.md
  package.json
  pnpm-lock.yaml
  Cargo.lock
```

这是一张目标地图，不要求工程初始化时创建每一项。

## 6. 模块与依赖规则

### 6.1 前端

```text
app → features → shared
```

- `app` 可以组合 Feature，不承载业务规则；
- Feature 之间不直接导入内部组件，通过路由、共享 DTO 或应用状态协调；
- `shared` 不反向依赖 Feature；
- React 组件不包含 SQL、文件绝对路径、Token 预算和复习算法；
- Tauri 调用集中在类型化客户端，不散落在按钮事件中。

### 6.2 Rust 核心

```text
commands → application → domain
                     ↘ ports ← infrastructure
```

- Command 只校验边界输入、调用用例、转换输出和错误；
- Application 决定事务与操作顺序；
- Domain 不依赖 Tauri、SQLite、HTTP、文件系统和 UI；
- Infrastructure 实现持久化和外部能力；
- `bootstrap` 是唯一知道具体实现如何组合的位置；
- Repository 返回领域对象或用例 DTO，不泄露 SQLite Row。

### 6.3 跨边界 DTO

DTO 需要：

- 使用明确字段和可演进版本；
- 日期、时间、ID 和错误码格式统一；
- 不返回 Rust 调试字符串和数据库内部字段；
- 不允许通过一个 `json: any` 规避类型设计；
- 大文件不通过 IPC JSON/Base64 传输；
- 进度事件只传 ID、阶段、数量和脱敏错误。

## 7. M1 正式模块

### 7.1 Workspace

职责：

- 创建和打开工作区；
- 解析工作区应用数据路径；
- 保存工作区元数据；
- 检查 schema 版本和文件完整性；
- 管理“最近打开工作区”引用。

M1 不提供复杂的多工作区 UI，只保留用例和数据边界。

### 7.2 Database

职责：

- 连接 SQLite；
- 启用外键并验证所需功能；
- 执行迁移；
- 提供事务边界；
- 生成迁移前数据库快照；
- 输出不含业务正文的健康状态。

M1 只建立支持验证所需的最少表：schema、workspace、blob、resource_document、processing_job。其余业务表进入对应里程碑时再迁移。

### 7.3 Blob Store

职责：

- 流式复制和 SHA-256；
- 内容寻址路径；
- 重复检测；
- 临时文件与原子提交；
- 完整性检查；
- 引用检查后的安全删除。

Blob Store 不负责 PDF 解析、OCR、资料分类或 AI 上传。

### 7.4 Background Jobs

M1 只支持导入和完整性检查任务。统一状态机可以保留，但不提前实现通用优先队列、并发池和插件式 Handler 注册。

### 7.5 Backup

职责：

- 生成 Manifest；
- 一致性复制数据库与 Blob；
- 校验哈希和 schema 版本；
- 恢复到临时目录；
- 验证后切换或创建新工作区。

M1 备份不含密钥和可重建缓存。加密备份暂缓，但格式需预留版本字段。

## 8. 错误模型

### 8.1 稳定错误结构

前端收到：

| 字段           | 说明                                  |
| -------------- | ------------------------------------- |
| `code`         | 稳定机器错误码，例如 `FILE_NOT_FOUND` |
| `message`      | 可面向用户显示的简短说明              |
| `action`       | 可选恢复建议，例如重新选择文件        |
| `operation_id` | 用于关联本地诊断日志                  |
| `details`      | 经过筛选的结构化细节，可选            |

### 8.2 首批错误域

- `WORKSPACE_*`
- `DATABASE_*`
- `MIGRATION_*`
- `FILE_*`
- `IMPORT_*`
- `BACKUP_*`
- `PERMISSION_*`
- `INTERNAL_ERROR`

内部错误链只进入脱敏日志，不能把绝对私有路径、SQL、密钥或资料正文直接展示给 UI。

## 9. 依赖策略

### 9.1 选择原则

引入依赖前回答：

1. 是否解决当前已存在的问题？
2. 标准库或已有依赖是否足够？
3. 是否活跃维护并有兼容许可证？
4. 是否显著增加安装体积、启动时间或攻击面？
5. 是否能在 Windows Release 构建中工作？
6. 是否容易替换或隔离在 Adapter 中？

### 9.2 版本锁定

- 提交 `pnpm-lock.yaml` 与 `Cargo.lock`；
- `package.json` 声明 package manager 和 Node 范围；
- 使用 `rust-toolchain.toml` 记录工具链；
- Spike 报告记录精确依赖版本；
- 依赖升级单独提交，不能与大功能修改混在一起；
- 不在文档中长期依赖 `latest`，只在初始化命令中使用并立即锁定结果。

### 9.3 M1 候选依赖类别

- Tauri 2 与官方必要插件；
- React + TypeScript + Vite；
- SQLite 驱动和迁移支持；
- 序列化、错误处理、哈希与日志；
- 前端单元测试与 Rust 内置测试工具；
- 不安装 React Flow、PDF.js、OCR 和 AI SDK 到正式工程，直到对应 Spike 形成决定。

## 10. 质量基线

### 10.1 TypeScript

- 启用严格模式；
- 禁止无说明的 `any`；
- 格式化、Lint、类型检查分开执行；
- UI 逻辑优先使用小函数和组合，不建立深层组件继承；
- 对 DTO 解析、错误映射和关键状态编写单元测试。

### 10.2 Rust

- `cargo fmt --check`；
- `cargo clippy` 将警告作为 CI 失败；
- `cargo test`；
- 领域规则测试不启动 Tauri 和 SQLite；
- Repository 集成测试使用独立临时数据库；
- 文件测试使用独立临时目录，不访问真实用户数据。

### 10.3 文档

- README 文档链接有效；
- 新技术决策有 ADR；
- Spike 有环境、样本、失败情况和结论；
- 架构或数据边界变化同步更新相关文档；
- 示例资料可以合法提交到公开仓库。

## 11. 测试分层

| 层级                 | 目标                   | M1 示例                       |
| -------------------- | ---------------------- | ----------------------------- |
| Domain 单元测试      | 验证纯规则             | Blob 路径生成、工作区状态判断 |
| Application 用例测试 | 验证操作顺序与失败补偿 | 导入成功、重复导入、取消导入  |
| Repository 集成测试  | 验证 SQLite 和事务     | 迁移、唯一约束、回滚          |
| 文件集成测试         | 验证真实文件行为       | 流式哈希、原子移动、损坏检测  |
| Command 契约测试     | 验证 IPC DTO 和错误    | 创建工作区、导入文件错误      |
| UI 单元/组件测试     | 验证状态展示           | 进度、失败、恢复建议          |
| 桌面 Smoke Test      | 验证完整打包路径       | 启动、创建工作区、关闭重开    |

M1 不追求覆盖率数字。关键失败路径必须有测试，覆盖率不能替代行为验收。

## 12. 日志与诊断

- 使用结构化本地日志；
- 每次跨层操作生成 `operation_id`；
- 默认记录事件名、耗时、状态和错误码；
- 不记录 PDF 正文、用户笔记、API Key、完整 Prompt 和绝对来源路径；
- 开发模式可以增加调试字段，但仍不能记录密钥；
- 诊断导出允许用户预览，并包含应用版本、schema、任务状态和脱敏日志。

## 13. CI 计划

M1 先建立 Windows CI，因为这是首要平台和 Tauri 当前验证目标。

建议检查顺序：

1. 文档和基本仓库检查；
2. pnpm 安装锁定依赖；
3. 前端格式、Lint、类型检查和测试；
4. Rust 格式、Clippy 和测试；
5. 前端构建；
6. Tauri Release 构建；
7. 保存非签名测试产物，仅用于项目验证。

macOS 和 Linux CI 在 Windows M1 稳定且对应平台有人实际验证后增加，不先制造无法维护的红色流水线。

- [x] 应用可以在无网络状态启动；

## 16. M1 完成定义

只有同时满足以下条件，M1 才算完成：

1. TV-01 至 TV-04 有明确结论；
2. ADR-001、002、003、004 已接受或记录替代方案；
3. 正式工程基于已接受结论初始化；
4. 工作区、SQLite、Blob、备份主路径通过验收；
5. 关键失败和恢复路径经过自动或可复现测试；
6. Windows Release 构建可运行；
7. 文档与实际工程一致；
8. 没有为了后续功能留下未使用的抽象层和依赖。

## 17. 进入 M2 的输入
