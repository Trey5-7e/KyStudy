## 要回答的问题

在 Windows 11、普通笔记本 CPU 和完全离线条件下，可选本地 OCR Worker 能否把中文扫描页
转换为足以用于搜索和 AI 上下文的文本与归一化文字框，同时不阻塞 PDF 阅读和手动题目管理？

## 不在范围内

- 不把实验代码直接接入正式 Tauri 应用；
- 不验证自动题目分割、答案区域检测、手写体或版面语义恢复；
- 不把普通 OCR 文本当作数学公式的可靠结构化结果；
- 不验证 macOS、Linux、ARM 或 GPU 推理；
- 不使用受版权保护的真实题库样本。

## 环境

| 项目     | 值                                     |
| -------- | -------------------------------------- |
| 操作系统 | Windows 11 专业版 10.0.26100 x64       |
| CPU      | AMD Ryzen 7 5800H，8 核 16 线程        |
| 内存     | 15.86 GiB                              |
| Python   | 3.12.8，独立环境位于 F 盘              |
| OCR      | RapidOCR 3.9.2 + PP-OCRv6 small        |
| 推理     | ONNX Runtime 1.27.0，CPU               |
| 图像     | OpenCV Python 5.0.0.93 + Pillow 12.3.0 |
| 打包     | PyInstaller 6.21.0，`onedir`           |
| 测量     | psutil 7.2.2，完整进程树 RSS           |

模型文件共 31,749,509 bytes（30.28 MiB），已随 RapidOCR 安装，不需要首次运行下载。

## 样本

四个样本由 `experiments/tv-07-ocr/tv07_ocr/fixtures.py` 确定性生成：

| 样本                      | 特征                            | SHA-256 前 12 位 |
| ------------------------- | ------------------------------- | ---------------- |
| `clean_chinese.png`       | 1400x1800，6 行清晰中文         | `99e53d891e29`   |
| `tilted_phone.jpg`        | 7 度旋转、轻微模糊和压缩        | `62587411d62a`   |
| `low_resolution_scan.png` | 300x400 降采样后放大到 900x1200 | `030144475696`   |
| `formula_table.png`       | 中文、递推式、条件概率和表格    | `a770ef929cdd`   |

生成图片和本机基准 JSON 位于忽略的 `output/` 目录，不提交仓库。

## 候选方案

1. Windows 系统 OCR：依赖 MSIX 包身份，不能覆盖当前无包身份的内部 EXE 主路径；
2. RapidOCR + ONNX Runtime 可选 sidecar：模型可随组件分发，CPU 和离线能力可测；
3. PaddleOCR 文档/公式完整流水线：能力更广，但模型、依赖和 CPU 成本超出本轮正文 OCR；
4. 外部 OCR API：增加隐私、网络和费用约束，不作为本地优先的默认路径。

## 通过标准

- [x] 普通中文正文足以用于搜索和 AI 上下文；
- [x] 返回置信度、页面尺寸和有效的归一化文字框；
- [x] 原图保留，公式不可靠时降级为区域图片；
- [x] 完全离线运行，不在首次识别时下载模型；
- [x] Worker 可取消，OCR 不成为 PDF 阅读和手动标记的前置条件；
- [x] Windows 独立目录可构建、启动和识别；
- [ ] 体积和内存足以无条件进入最小安装包。

## 实验步骤

1. 在项目外创建 Python 3.12 环境并锁定依赖；
2. 生成四类无版权样本，先人工确认样本非空且内容正确；
3. 以常驻 Worker 对每个样本识别 3 次，测量 CER、召回、耗时和完整进程树 RSS；
4. 设置无效 HTTP/HTTPS 代理执行单次识别，验证不依赖网络；
5. 启动后主动终止 Worker，验证 2 秒内退出且不需要强制杀进程；
6. 使用 PyInstaller 构建 `onedir`，对打包 EXE 重复离线、协议和取消测试；
7. 记录首次打包失败、VC Runtime 根因和修复后的结果。

## 结果

### 识别效果与速度

| 场景         | CER   | 关键词召回 | 平均墙钟时间 | 平均置信度 | 文字框 |
| ------------ | ----- | ---------- | ------------ | ---------- | ------ |
| 清晰中文     | 0.00% | 100%       | 1015.30 ms   | 0.9911     | 有效   |
| 倾斜手机照片 | 0.00% | 100%       | 593.54 ms    | 0.9997     | 有效   |
| 低分辨率扫描 | 0.00% | 100%       | 439.99 ms    | 0.9997     | 有效   |
| 公式与表格   | 1.79% | 100%       | 894.35 ms    | 0.9715     | 有效   |

这组样本只能证明技术路径成立，不能代表真实教材、双栏、噪声扫描、手写体和复杂公式的
最终准确率。公式样本即使本次 CER 较低，也仍标记为图片降级场景。

### 资源、离线和取消

| 场景                         | 结果                                   |
| ---------------------------- | -------------------------------------- |
| 源码 Worker 初始化           | 863.94 ms                              |
| 源码 Worker 连续基准峰值 RSS | 759.20 MiB，包含 Windows Python 子进程 |
| 源码离线单次调用             | 成功，3871.32 ms 墙钟时间              |
| 源码 Worker 取消             | 2.86 ms，无强制 kill                   |
| 打包目录                     | 258,142,230 bytes（246.18 MiB）        |
| 打包 Worker 连续 12 次       | 平均 694.88 ms，最大 1082.36 ms        |
| 打包 Worker 峰值 RSS         | 728.88 MiB                             |
| 打包 Worker 离线协议         | `ready -> result -> stopped`，退出码 0 |
| 打包 Worker 取消             | 134.77 ms，无强制 kill                 |

源码环境目录为 341,470,768 bytes，但包含 Ruff、PyInstaller 和其他验证工具，不能当作正式
运行时体积。正式体积以打包目录为准。

### 失败与边界样本

第一次 PyInstaller 构建能够完成，但独立 EXE 在加载 `onnxruntime_pybind11_state` 时失败。
产物混入 Microsoft Store Python 自带的 VC Runtime 14.36，而系统中正常运行 ONNX Runtime
的是 14.51。替换四个旧 DLL 后立即恢复；构建脚本现会比较版本并只覆盖更旧的副本。
ONNX Runtime 官方也要求 Windows Visual C++ 2019 Runtime，并推荐最新版本。

当前打包体积和峰值内存不适合让 OCR 常驻或强制进入每个用户的最小安装包。真实复杂页、
长批次内存回落、组件更新和无开发环境电脑仍需在正式接入时继续验证。

### 恢复与降级

- OCR 组件缺失、失败或被取消时，原 PDF、图片、文字层和手动区域框选仍可使用；
- 每个识别结果都关联原始页/区域，用户可人工纠正或直接查看图片；
- 公式、矩阵、复杂表格和低置信结果保留区域图片，不生成未经核对的公式语义；
- Worker 是可终止进程，父进程取消后不写入半成品正式记录；
- 模型随可选组件提供，离线时不进入下载失败状态。

## 结论

`conditional`。RapidOCR + PP-OCRv6 small + ONNX Runtime CPU 能满足 Windows 本地中文正文
OCR 的速度、离线、文字框和取消要求，适合作为 M10 的首选技术路径。条件是：Worker
必须按需启动并在批次结束后退出；作为可选组件分发；原图和人工流程始终保留；公式不
当作可靠文本；正式集成前补充真实资料与无开发环境电脑验收。

## 建议决策

采用受控本地 sidecar，而不是把 Python/OCR 依赖嵌入 Tauri 主进程。Rust 后端负责组件
可用性、内部路径、任务状态、取消、超时和稳定错误码；WebView 只接收经过裁剪的 OCR
结果 DTO。最小安装包暂不强制包含 OCR，外部 OCR API 未来只能作为同一 Port 后的显式
可选方案。
