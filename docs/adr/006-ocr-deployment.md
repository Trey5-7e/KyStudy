## 上下文

KyStudy 要处理扫描 PDF、图片规划和错题区域，但文字型 PDF 已有文字层与本地索引，OCR
不能成为阅读或手动录入的强制前置条件。桌面应用需要本地优先、离线、可取消和不消耗云端
Token，同时要控制主安装包体积、主进程稳定性、内存和第三方模型许可。

TV-07 证明 Python OCR 可以打包为独立 Windows 进程，也暴露了 246.18 MiB 目录体积、
约 728.88 MiB 连续运行峰值 RSS 和 VC Runtime 版本冲突。公式样本的单次高准确率不足以
证明公式语义可靠。

## 决策驱动因素

- OCR 默认在本地完成，不上传用户题目和资料；
- 模型随组件提供，不在首次使用时临时下载；
- OCR 崩溃、取消或缺失不影响主应用和原文件；
- 能返回中文文本、置信度和归一化文字框；
- 不让 Python/ONNX Runtime 依赖污染 Tauri 主进程；
- 最小安装包和空闲内存不承担可选能力的全部成本；
- 为未来替换引擎或显式外部 OCR 保留稳定 Port。

## 候选方案

### 方案 A：系统 OCR

依赖较少，但当前 Windows 系统 OCR 路径需要 MSIX 包身份，不能覆盖无包身份内部 EXE，
跨平台和模型行为也不统一。

### 方案 B：RapidOCR Python Sidecar

PP-OCRv6 small 模型可离线随组件提供，ONNX Runtime CPU 在目标笔记本上速度达标；独立
进程能隔离依赖、资源和崩溃。代价是目录体积、内存、Python 打包和 VC Runtime 维护。

### 方案 C：Rust/C++ 直接调用 ONNX Runtime

可能减少 Python 和无关依赖，但需要自行实现图像预处理、检测、文字识别、后处理和模型
升级兼容。本轮没有证据证明额外维护成本能够换来足够收益。

### 方案 D：外部 OCR API

可以转移本机资源成本，但引入网络、隐私、费用、Token/配额和供应商错误，不符合默认
本地优先。未来可作为用户显式配置的替代适配器。

## 决策

Windows 首批 OCR 采用**可选、受控、按需启动的本地 sidecar**：

1. 候选实现锁定 RapidOCR 3.9.2、PP-OCRv6 small 和 ONNX Runtime 1.27.0 CPU；正式接入
   时再根据兼容性测试决定是否升级；
2. OCR 组件不进入最小安装包。用户首次主动使用 OCR 时，应用说明约占空间、版本和
   离线属性，并提供安装、移除和完整性校验；
3. 模型随组件安装，不在识别时联网下载；
4. Rust 后端通过逐行 JSON 协议管理 Worker，只在内部传递受控临时图片路径；WebView
   DTO、日志和诊断导出不得包含路径；
5. Worker 返回稳定 schema：文本、置信度、页面尺寸和归一化文字框；原始引擎错误映射
   为稳定错误码，不向前端返回堆栈或第三方原文；
6. 默认先使用 PDF 文字层，只有用户明确触发时才 OCR 扫描页或选中区域；批次结束、
   取消、超时或应用退出时终止 Worker，不常驻；
7. 原 PDF 和区域图片始终保留。公式、矩阵、复杂表格和低置信结果只作为候选文本，必须
   支持图片降级与人工纠正，不能据此自动写入公式语义；
8. 外部 OCR 将来只能实现相同 Port，并要求用户显式选择和确认外发范围，不做静默回退。

## 理由与证据

TV-07 的三类普通中文样本 CER 为 0、关键词召回为 100%，公式表格样本 CER 为 1.79%；
单页平均约 0.44–1.02 秒。离线调用、正常关闭和强制取消均通过，独立 EXE 连续 12 次
平均 694.88 ms。

打包失败说明 Python sidecar 仍有运行库风险，因此构建必须验证实际 EXE，而不能只看
PyInstaller 退出码。构建脚本会用系统更新的 VC Runtime 替换 Microsoft Store Python
可能带入的旧副本；发布阶段还要在干净 Windows 电脑复验。

## 后果

### 正面

- OCR 不消耗云端 Token，不默认外发资料；
- OCR 故障和高内存与 Tauri 主进程隔离；
- 原有 PDF 阅读、文字层、本地搜索和手动框选继续独立工作；
- 以后可以在不改变产品用例的前提下替换为原生引擎或显式外部适配器；
- 模型预装于可选组件，离线行为确定。

### 代价与限制

- 当前可选目录约 246.18 MiB，连续批次峰值 RSS 约 728.88 MiB；
- 要维护 Python 锁文件、PyInstaller、VC Runtime、组件版本和许可证清单；
- 合成样本不足以代表真实教材、手写体、双栏和复杂公式；
- 首批先支持 Windows x64，其他平台必须独立验证和打包；
- 组件安装、更新、损坏恢复和磁盘占用需要额外产品界面。

### 后续行动

- 实现 Rust 进程监督、超时、取消、并发限制和临时文件清理；
- 增加真实但可合法使用的 M10 验收集；
- 优化 OpenCV 与 PyInstaller 体积，评估原生 ONNX Runtime 的维护收益；
- 生成实际分发目录的第三方许可证和模型归属清单；
- 在无开发环境 Windows 电脑验证安装、升级、离线和卸载数据保留。

## 复审条件

出现以下任一情况时重新评估：真实普通中文 CER 无法支持搜索；峰值内存导致目标设备
明显卡顿；可选组件仍无法接受；RapidOCR/模型停止维护或许可证改变；原生 Rust/C++
方案能以可维护成本显著降低体积；KyStudy 正式支持 Windows 以外的平台。
