## 上下文

KyStudy 需要保存用户导入的 PDF、图片和思维导图源文件。文件可能达到 1 GB，不能整体加载进内存，也不能依赖用户原路径永久存在。SQLite 与文件系统不能共享一个原子事务，因此必须明确中断、提交失败和异常退出后的恢复协议。

完整备份还必须把 SQLite 与正式 Blob 放在一起，同时排除密钥、staging 和可重建缓存，并允许恢复到不同绝对目录。

## 决策驱动因素

- 大文件导入的固定内存与取消能力；
- 本地资料长期可用，不依赖外部原路径；
- 同内容物理去重和可验证完整性；
- 文件与数据库跨介质提交的可恢复性；
- Windows 文件锁、同盘提交与异常退出行为；
- 备份可移植、可校验且不会覆盖现有工作区；
- 依赖规模、开源许可证和跨平台能力。

## 候选方案

### 方案 A：内容寻址文件库 + SQLite 元数据

导入到工作区 staging，同步计算 SHA-256，再无覆盖提交到由哈希生成的相对路径。SQLite 保存 Blob、ResourceDocument 和恢复 Job。

优点：

- 文件流式处理，数据库保持较小；
- 哈希同时承担去重、路径和完整性依据；
- 多个资料对象可以引用同一个物理文件；
- Blob 可独立复制、校验和备份。

限制：

- 文件提交与数据库事务之间需要持久化恢复协议；
- 必须处理 staging、未登记正式文件和引用安全删除；
- 完整备份不是单个数据库文件。

### 方案 B：只登记用户原文件路径

优点是导入快且不占第二份空间；缺点是用户移动、删除、U 盘拔出或权限变化都会使资料失效，备份也无法自包含。

### 方案 C：把原文件保存为 SQLite BLOB

优点是事务和备份边界单一；缺点是 300 MB–1 GB 文件会增加数据库写放大、WAL、恢复和备份压力，也不利于 PDF 引擎按文件路径读取。

### 方案 D：随机文件名 + 数据库映射

实现简单，但无法从路径直接判断内容，重复检测与孤立文件扫描都更依赖数据库状态。

## 决策

采用方案 A。正式路径采用 SHA-256 生成的相对 storage key，不保留用户绝对路径。数据库只保存相对键、Blob 元数据、ResourceDocument 引用和持久化导入 Job，前端不能提交任意 storage key、任意写入目标或任意 SQL。

导入使用同一工作区所在磁盘的 staging，固定 1 MiB 堆缓冲区边复制边计算 SHA-256，并在空间检查和预分配成功后开始写入。`running` Job 用于识别尚未形成可信文件的复制，`committing` Job 保存哈希、大小和相对键，用于文件提交后 SQLite 事务失败时继续完成提交。

完整备份采用版本化目录格式：Manifest、SQLite Online Backup 一致快照和相对 Blob 树。恢复必须先在临时同级目录验证格式版本、schema 版本、数据库、相对路径、大小和 SHA-256，再切换到不存在的新目标。压缩、分卷和加密属于后续可叠加的外层传输格式，不改变内部相对路径与哈希清单。

## 理由与证据

- Rust 标准库建议使用原子创建避免 TOCTOU，`fs::rename` 要求源和目标位于同一挂载点；
- `tempfile` 提供同目录安全临时文件和 `persist_noclobber`；
- `fs4` 提供 Windows/Unix 可用空间、预分配和 advisory lock；
- TV-02 已证明 SQLite 事务、恢复 Job 和 Online Backup API 可用；
- TV-03 的 5 个单元测试和 11 个跨模块测试覆盖去重、取消、来源变化、空间不足、工作区锁、进程异常退出、数据库事务失败、Blob 缺失/损坏、备份损坏、路径穿越、授权边界和跨绝对路径恢复；
- TV-03 本机 release 实测：10 MiB、300 MiB、1 GiB 首次导入分别为 31 ms、488 ms、1,352 ms；重复导入 1 GiB 为 2,161 ms，未产生第二个物理 Blob；
- 包含约 1.30 GiB 数据的完整备份和恢复分别为 3,916 ms 与 3,874 ms，备份大小为 1,398,846,402 bytes；
- 测量进程峰值工作集为 7.46 MiB、峰值分页内存为 2.12 MiB，证明实验实现的内存占用不随 1 GiB 文件线性增长；
- `cargo fmt --check`、`cargo test --locked` 与全目标/全特性 Clippy 零警告通过。完整证据与复现命令见 [TV-03](../spikes/TV-03-blob-store.md)。

## 后果

### 正面

- 用户原文件移动后不影响工作区；
- 大文件处理保持固定内存；
- 同一工作区内天然支持物理去重；
- Blob、数据库和备份都可以独立做哈希校验；
- 恢复到不同绝对目录不需要重写数据库路径。

### 代价与限制

- 导入需要额外磁盘空间，最坏情况下临时同时存在来源和 staging；
- 首次导入必须完整读取文件并计算哈希；
- 文件系统与 SQLite 之间依赖 Job 恢复而非真正的跨资源原子事务；
- 目录备份便于验证但不便于直接传输，后续可能增加归档层；
- advisory lock 不能阻止不遵守协议的外部程序修改文件。

## 复审条件

- 1 GB 导入、备份或恢复的时间/空间不可接受；
- PDF 引擎无法稳定读取内容寻址路径；
- 移动平台文件系统不支持所需的同盘提交或锁语义；
- 用户明确需要“引用原文件而不复制”的可选模式；
- 目录备份无法满足实际传输、云盘或版本管理需求。
