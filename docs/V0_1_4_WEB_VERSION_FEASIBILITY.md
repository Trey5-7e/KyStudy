# KyStudy v0.1.4 网页版可行性分析

> 状态：技术预研结论，不代表已经开始云端上线或改变桌面端的数据边界。
>
> 本文针对当前 v0.1.4 的公式渲染、OCR、AI 对话和做题本 PDF 流程，说明哪些能力可以直接复用、哪些能力必须增加服务端，以及推荐的渐进式发布路线。

## 1. 结论先行

KyStudy 可以发布网页版，但不能把当前 Tauri 构建产物直接“改成网页”。当前前端页面大多可以复用，数据和能力层需要增加 Web API、身份认证、云端文件存储和异步 OCR/索引任务。

建议采用“双端共用前端、能力分层”的路线：

1. 桌面端继续作为离线优先版本，保留 SQLite、本地 PDF、离线 OCR 和本地密钥存储。
2. 先发布一个不接触真实用户文件的网页版演示/只读版，用来验证 AI 对话、题库浏览和公式显示。
3. 再增加登录、云端资料上传、云端索引和 OCR，形成可用的云端工作区。
4. 桌面端与网页版共享数据契约和 Markdown/公式渲染契约，不强行共享 Tauri 命令实现。

当前公式渲染已经切换到 `react-markdown + remark-gfm + remark-math + rehype-mathjax`。MathJax SVG 不依赖浏览器本地数学字体基线，桌面 WebView 和网页版可以共用同一套渲染结果；这会降低“浏览器预览正常、桌面错位”的概率，但不能替代真实桌面验收。

## 2. 当前桌面架构边界

| 能力                            | 当前实现                           | 网页版是否可直接复用             | 需要的替代层                              |
| ------------------------------- | ---------------------------------- | -------------------------------- | ----------------------------------------- |
| React 页面、路由、表单、对话 UI | `src/app`、`src/features`          | 大部分可以                       | 将 `invoke` 调用改为 Web API client       |
| AI 对话与 Provider 配置         | Tauri command + Rust Provider 适配 | UI 可以，密钥和请求不能直接复用  | 服务端 API Gateway、密钥加密、限流和审计  |
| Markdown/公式                   | `MarkdownRenderer` + MathJax SVG   | 可以直接复用                     | 浏览器只承担渲染，不读取本地数据          |
| 题库与复习记录                  | SQLite migrations、Rust repository | 数据模型可以复用，数据库连接不能 | PostgreSQL/SQLite Server + API + 迁移脚本 |
| PDF 阅读                        | PDF.js + 本地文件/资源协议         | PDF.js 可以复用                  | 对象存储、受控下载 URL、断点上传          |
| PDF 文字索引                    | 本地索引器和 Tauri 文件访问        | 算法可复用，文件入口不能         | 服务端解析 Worker、任务队列、索引存储     |
| OCR                             | 本地 RapidOCR/ONNX sidecar         | 不能在浏览器直接假设存在         | 服务端 OCR Worker；可保留桌面离线 OCR     |
| AI 资料上下文                   | 本地 Blob、SQLite 元数据           | UI 可以复用，数据读取不能        | 服务端检索/RAG 或受控片段 API             |
| 备份恢复                        | 本地 SQLite/Blob 一致快照          | 不能直接下载本地路径             | 云端快照、对象存储版本和导出包            |
| 文件权限与密钥                  | Tauri 权限、Windows 凭据存储       | 不适用                           | 账号、会话、服务端 KMS/Secret Manager     |

关键边界集中在 `src/shared/tauri`、`src-tauri/src/commands`、`src-tauri/src/infrastructure/sqlite_*`、`src/features/library/pdf` 和 `src-tauri/src/infrastructure/ocr_worker.rs`。这些模块不应通过浏览器 polyfill 伪装成成功，而应明确分为 Web API 或桌面专属能力。

## 3. 推荐网页版架构

### 3.1 前端

- 继续使用 React + Vite，复用现有页面、设计 token 和 `MarkdownRenderer`。
- 新增 `src/shared/web` 或独立 `web-client`，实现与 `src/shared/tauri` 等价的 API client。
- 预览模式只使用 `src/preview` 的确定性 fixture；不读取浏览器的用户 SQLite、路径或隐私存储。
- PDF 阅读保留 PDF.js，但文件来源改成带权限校验的对象存储 URL/流式接口。

### 3.2 服务端

推荐将现有 Rust domain/application 层逐步抽取为可被 Tauri 和 HTTP 共用的 crate；HTTP 层可以使用 Rust Web 框架，也可以先采用团队熟悉的 TypeScript 服务。第一阶段不建议直接把 Tauri command 暴露到公网。

服务端至少包含：

- 认证和会话：账号、登录、刷新、注销、设备管理；
- 工作区 API：资料、题库、题目、计划、复习记录；
- AI Gateway：统一 Provider、模型、超时、重试、流式响应和错误契约；
- 文件 API：预签名上传、断点续传、病毒/类型检查、权限校验；
- 任务队列：PDF 解析、OCR、切题、索引和失败重试；
- 审计与限流：请求量、Token、文件大小、任务状态和异常追踪。

### 3.3 数据与基础设施

- 结构化数据：生产环境优先 PostgreSQL；单用户自部署可保留服务器端 SQLite。
- 原始 PDF、题图和 OCR 中间产物：S3/MinIO 等对象存储，不放入数据库大字段。
- 检索：第一阶段使用 PostgreSQL 全文检索；需要语义检索时再增加向量索引，避免一开始引入过多基础设施。
- Worker：OCR、PDF 解析和 AI 长任务必须异步化，前端通过任务 ID 轮询或 SSE/WebSocket 获取进度。
- 密钥：用户 Provider Key 加密存储，默认不进入日志、备份和前端 bundle；更安全的方案是服务端托管 Provider Key，用户只保存工作区授权。

## 4. 发布路线

### 阶段 A：网页版演示/只读版（低风险）

目标是验证页面和公式，不接收真实私密资料。

- 使用预览 fixture 展示 AI 对话、题库浏览、OCR 公式样例和 AI 分析样例；
- 支持 MathJax SVG、长公式横向滚动、窄窗口布局；
- 明确显示“预览数据，不连接本地 SQLite/PDF/OCR/Provider”；
- 可部署到静态托管，不需要账号和用户文件系统。

### 阶段 B：云端工作区 MVP（中等风险）

- 登录和单用户工作区；
- 上传做题本 PDF，显示上传和解析进度；
- 服务端建立 PDF 文字索引；
- OCR Worker 只处理用户主动提交的页面/题目区域；
- AI 对话只发送用户选择的资料片段，并显示外发范围；
- 提供导出包，保证用户可以取回题库和资料元数据。

### 阶段 C：桌面/网页同步（高风险）

- 桌面端增加登录和可选云同步；
- 设计题目、题图、OCR 草稿、确认状态的冲突策略；
- 大文件和长任务支持断点续传、幂等重试；
- 增加多设备撤销、备份恢复、配额和运维监控；
- 对云端 Provider 与本地 Provider 明确优先级和隐私提示。

## 5. 主要风险与控制措施

| 风险               | 影响 | 控制措施                                                       |
| ------------------ | ---- | -------------------------------------------------------------- |
| API Key 泄露       | 高   | 不让浏览器直接持有供应商 Key；服务端加密、脱敏日志、轮换       |
| 用户 PDF/题库隐私  | 高   | 明确授权范围、对象存储 ACL、短期下载 URL、删除任务和审计       |
| OCR 成本与并发     | 中高 | 队列、配额、取消、重试上限、按页计费/限流                      |
| 大文件上传失败     | 中高 | 分片上传、断点续传、校验和、幂等任务                           |
| 桌面与网页数据冲突 | 高   | 版本号、操作日志、冲突 UI；不要用最后写入覆盖全部内容          |
| 公式渲染差异       | 中   | 共享 MathJax SVG 渲染器和 fixture；桌面仍做 WebView 验收       |
| 服务端运维与备份   | 高   | PostgreSQL 备份、对象存储版本、监控、告警和灾备演练            |
| 版权与合规         | 高   | 用户自有资料声明、删除机制、隐私政策、日志最小化和区域合规评估 |

## 6. 对 v0.1.4 的具体建议

本版本不建议直接承诺“网页版正式发布”。应先完成下面三项可逆工作：

1. 固化共享数据契约：AI 对话、附件、题目 OCR 草稿、模型列表和错误码；
2. 抽象 API client 接口：让 React 页面不再直接依赖 `invoke` 的返回细节；
3. 增加网页版预览入口和 CI 构建，确认 MathJax SVG 在桌面 WebView、普通 Chromium 和窄窗口均可读。

达到阶段 B 前，不要把真实 PDF、OCR 结果或 Provider Key 接入静态网页版。达到阶段 C 前，也不要把桌面 SQLite 当作远程数据库直接暴露。

## 7. 立项判断

网页版技术上可行，最大的工作量不是页面重写，而是数据、文件、OCR 和 AI Provider 的服务端化，以及隐私/运维责任的建立。推荐把网页版定位为“云端工作区”，而不是替代桌面离线版：

- 需要离线 OCR、本地资料隐私和一次性导入时，继续使用桌面端；
- 需要跨设备访问、云端 AI 和协作备份时，使用网页版；
- 两端通过稳定的资源/题目/对话契约同步，而不是共享实现细节。

因此，v0.1.4 可以开始网页版阶段 A 的预览和 API 边界设计；正式云端上传、OCR 和同步应作为后续版本的独立发布边界。
