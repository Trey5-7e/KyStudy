# Codex 内置浏览器 UI 设计、渲染与自检闭环

本文是 KyStudy 前端 UI 任务的 Agent 操作规程。目标是让 Agent 在提交 UI 改动前自行发现明显的布局、遮挡、溢出和交互问题，减少依赖项目维护者逐张截图指出问题。

这套流程不是“写完代码后截一张图”，而是一个必须反复执行的闭环：

```mermaid
flowchart LR
    A[明确页面目标与状态] --> B[先设计布局与交互约束]
    B --> C[实现组件与样式]
    C --> D[启动 Vite 预览]
    D --> E[用 Codex 内置浏览器渲染]
    E --> F[检查多视口、多状态和交互]
    F --> G{发现问题?}
    G -- 是 --> H[记录问题并优化设计]
    H --> C
    G -- 否 --> I[运行目标检查并提交验收证据]
```

## 1. 强制原则

1. 任何可见 UI 改动都必须完成“设计 → 实现 → 内置浏览器渲染 → 自检 → 优化 → 再渲染”至少一轮；只通过 TypeScript、Rust 或构建检查，不代表 UI 已完成。
2. 首次渲染必须主动检查，不等待项目维护者指出明显错误。尤其要检查空状态、长文本、窄窗口、弹层遮挡、菜单偏移和滚动行为。
3. 浏览器预览证明的是前端布局和交互状态；它不证明真实 SQLite、PDF、OCR、AI 或文件系统数据正确。真实数据边界必须由桌面验收或专门的后端测试覆盖。
4. 不启动 Release EXE 做 UI 调试。开发预览使用 Vite 页面；桌面 EXE 仍由项目维护者按验收文档执行。
5. 不读取浏览器 Cookie、Local Storage、密码或用户会话存储来“制造”数据。预览数据必须来自显式、可重复的 fixture 或只读预览后端。

## 2. 开始前：先写设计约束

在修改 JSX、CSS 或交互逻辑前，先用简短文字确定以下内容：

- 页面唯一目标和主要操作是什么；
- 内容层级：标题、说明、筛选区、主内容、辅助信息、危险操作分别放在哪一层；
- 页面需要支持哪些状态：加载中、空数据、正常数据、长文本、错误、禁用、保存中；
- 目标视口：至少桌面宽度、窄桌面宽度和手机宽度各一个；
- 交互边界：点击、悬停、键盘焦点、滚轮、拖动、弹层关闭和页面外点击的预期行为；
- 哪些内容依赖真实 Tauri 数据，哪些内容允许使用浏览器预览 fixture。

设计约束应先解决结构问题，再决定颜色、阴影和装饰。不要先堆叠局部 `margin` 或 `z-index`，之后再用补丁掩盖布局问题。

## 3. 实现阶段的要求

- 优先复用项目已有的页面容器、标题、按钮、表单、状态面板和弹层组件。
- 保持语义 HTML：按钮使用 `button`，导航使用链接或可聚焦控件，输入框有可见标签或可访问名称。
- 让布局由网格、弹性布局、最大宽度和间距 token 控制，避免依赖固定像素定位内容。
- 长标题、长路径、长错误信息和空列表必须有明确的换行、截断或滚动策略。
- 弹层、下拉菜单和行菜单必须明确所属定位上下文、层级和点击外部关闭规则。
- 不为浏览器预览增加会改变桌面真实行为的特殊逻辑；预览适配应集中在预览后端或数据适配层。

本仓库当前的浏览器预览入口位于 `src/preview`。预览后端只提供 UI 检查所需的只读数据，未覆盖的写入、真实 PDF、OCR 和 AI 请求应明确返回不支持状态，而不是伪造成功。

## 4. 启动与选择 Codex 内置浏览器

### 4.1 启动开发页面

在仓库根目录启动 Vite：

```powershell
pnpm dev
```

默认开发地址为 `http://127.0.0.1:1420/`。已有开发服务时复用它，不要重复启动多个服务；如果端口不同，以终端实际输出为准。

常用预览入口：

- `http://127.0.0.1:1420/#planning`：计划页面；
- `http://127.0.0.1:1420/#workbook`：题库页面；
- `http://127.0.0.1:1420/#library`：资料和思维导图页面。

### 4.2 使用内置浏览器

用户明确要求“Codex 内置浏览器”时，必须选择内置浏览器，不要替换成 Chrome、外部浏览器或仅凭代码推测页面效果。

操作顺序：

1. 复用当前已连接的内置浏览器绑定；没有绑定时选择 `iab`。
2. 首次连接后完整读取该浏览器提供的操作文档，按照文档中的 tab、导航、截图、可见文本和交互 API 操作；不要猜测未记录的 API 名称。
3. 复用已有目标 tab；如果 tab 已关闭或失效，只重新获取 tab，不重新初始化整个浏览器连接。
4. 导航到目标 Vite URL，等待页面完成渲染后再检查；页面尚未稳定时不要根据半成品截图下结论。
5. 每轮至少保留一张基线截图和一张修复后截图，或记录等价的可见状态证据。

浏览器工具初始化和 tab 操作以当前 Codex 浏览器技能文档为准。不要在文档中硬编码会随工具版本变化的内部连接细节；重点是保持“连接一次、复用绑定、导航、渲染、检查、再次渲染”的顺序。

## 5. 首次渲染检查清单

### 5.1 布局和视觉层级

- 页面标题、说明和主要操作是否在同一个清晰的头部层级；
- 选择栏、卡片、表格和状态面板是否保持一致的宽度、间距、边框和圆角；
- 没有数据时，选择器不会被撑高、挤扁或错位，空状态文案位于正确容器内；
- 内容没有被弹层、滚动条、固定底栏或相邻卡片遮挡；
- 行菜单、下拉菜单和弹窗的定位与触发控件对齐，层级不会被预览画布覆盖；
- 页面不会出现无意义的双滚动条、横向溢出或被裁剪的右侧操作；
- 长中文标题、英文 URL、题目公式和错误文案不会把布局撑破；
- 主操作、次操作和危险操作有清晰的视觉优先级。

### 5.2 状态矩阵

至少检查以下状态，而不是只检查“有数据”的默认状态：

| 状态        | 必查内容                                         |
| ----------- | ------------------------------------------------ |
| 加载中      | 有明确的加载反馈，不出现空白或闪烁的半成品布局   |
| 空数据      | 选择控件保持稳定，空状态说明下一步操作           |
| 正常数据    | 信息层级、行高、滚动和主要操作清晰               |
| 大量数据    | 列表、表格或画布可滚动，首屏操作仍可访问         |
| 长文本      | 标题、文件名、错误信息可换行或截断，不能覆盖按钮 |
| 错误        | 错误面板有稳定尺寸、可读文案和重试入口           |
| 禁用/保存中 | 按钮状态明确，不允许重复提交或误触发             |
| 弹层打开    | 背景、层级、焦点和关闭路径正确                   |

### 5.3 交互和可访问性

- 鼠标点击、悬停和键盘焦点都有可见反馈；
- Tab 顺序符合视觉顺序，弹层打开后焦点不会丢失；
- Enter、Escape、方向键和左右/上下翻页符合页面约定；
- 点击菜单外部可以关闭菜单，但点击菜单内部不会误关闭；
- 关闭按钮、取消按钮和返回按钮语义清晰，嵌套窗口的取消不会把用户带出错误层级；
- 滚轮、拖动和画布缩放不会被外层页面或透明遮罩吞掉；
- 触控尺寸足够，文字与背景有足够对比度；
- 表单输入有标签、占位提示或错误提示，错误不会只靠颜色表达。

## 6. 多视口和回归路径

每次 UI 改动至少检查以下视口组合；如果浏览器工具不能直接调整视口，就使用当前可用窗口并记录限制：

1. 宽桌面：约 `1440 × 900`；
2. 普通桌面：约 `1280 × 800`；
3. 小桌面或窗口化：约 `1024 × 768`；
4. 窄窗口：约 `640px` 宽；
5. 手机宽度：约 `360px` 宽。

每个视口至少检查一次首屏和一次滚动后的内容。对弹层、行菜单、题目预览和思维导图等高风险区域，还要检查“打开 → 互动 → 点击外部/返回 → 再次打开”的完整路径。

UI 修复完成后，回到受影响页面的相邻入口做一次回归。例如修改题库行菜单时，同时检查题库空状态、题目浏览、资料入口和弹层关闭；修改组卷筛选时，同时检查默认值、筛选结果和生成按钮状态。

## 7. 浏览器预览不能读取本地数据时怎么办

这是预期边界，不是继续向浏览器注入用户数据库的理由。

### 浏览器可以验证

- 页面结构、响应式布局、字体、颜色、间距、边框和层级；
- 加载、空、错误、正常和大量数据状态；
- 前端筛选、展开、切换、菜单、弹层、键盘和滚动交互；
- 只读预览数据下的题库、资料、计划和思维导图展示。

### 浏览器不能证明

- 本地 SQLite 是否可打开、迁移是否成功、真实数据是否完整；
- 本地 PDF、OCR sidecar、文件权限和资源协议；
- Tauri 命令的写入、事务、备份恢复和进程并发；
- AI Provider、网络请求和系统级窗口行为。

### 推荐做法

1. 为 UI 状态提供稳定、最小化的 preview fixture；同一个 fixture 应可重复渲染。
2. 通过预览适配层返回明确的 `BROWSER_PREVIEW_UNSUPPORTED`，不要在浏览器里静默伪造写入成功。
3. 用浏览器完成视觉和前端交互检查后，再用 Rust/前端测试覆盖真实数据契约。
4. 真实工作区、PDF、OCR、备份和迁移由桌面验收文档验证；不要把浏览器截图当作数据验收证据。

## 8. 发现问题后的迭代方法

每轮检查后先记录问题，再改代码。问题至少包含：页面/URL、视口、状态、现象、预期、可能原因和优先级。

- **P0**：白屏、数据误写、主要操作不可用、页面无法关闭或严重遮挡；立即停止其他 UI 工作并修复。
- **P1**：核心流程受阻、筛选/菜单/键盘/滚动失效、窄窗口不可用；本轮必须修复。
- **P2**：间距、字号、对齐、文案和装饰细节；核心流程稳定后修复。

修复顺序应是：结构和容器 → 定位和滚动 → 交互层级 → 响应式 → 字体间距 → 颜色和装饰。每次修复后重新导航并检查原问题和相邻路径，不能只修改 CSS 后凭代码判断已解决。

## 9. 交付前门槛

只有同时满足以下条件，Agent 才能在汇报中说“UI 改动已完成”：

- 已按本文闭环完成至少一轮；
- 宽桌面、普通桌面和至少一个窄视口通过；
- 加载、空数据、正常数据、错误和长文本状态没有明显布局问题；
- 主要鼠标和键盘交互通过，弹层和菜单没有遮挡或错误关闭；
- 没有未解释的 P0/P1 问题；
- 修改文件已通过目标检查：

```powershell
pnpm check:target -- <changed-files>
```

- 批次准备交付时，再按 [开发工作流](DEVELOPMENT_WORKFLOW.md) 执行完整门禁；
- 汇报中包含预览 URL、视口、检查状态、剩余限制和目标检查结果。
