## 实现范围

### 明确延期

- 只有 `todo` 和 `in_progress` 任务可以调整计划日期；
- `done` 任务必须先重新打开，`canceled` 任务必须先恢复；
- 新日期必须是合法本地日历日期；
- 延期必须填写去除首尾空格后 1～500 个字符的原因；
- 新旧日期相同时不能提交，也不会制造变化历史；
- 延期只修改 `planned_date` 和 `updated_at`，不修改标题、科目、优先级、状态或完成时间；
- 日期更新、原/新快照和 `rescheduled` 历史在同一个 SQLite `IMMEDIATE` 事务中提交；
- 延期成功后任务从原日期列表移除，界面明确提示新日期；用户切换到新日期后可以继续查看任务。

`task_change.reason` 继续保持数据库可空，因为创建、编辑和状态变化不需要原因；但 M2-005 的 `reschedule_task` 用例要求延期原因非空。

### 取消与恢复

状态机增加：

```text
todo --------cancel-------> canceled
in_progress--cancel-------> canceled
canceled ----restore------> todo
```

- 已完成任务不能直接取消；
- 待开始或学习中任务不能执行“恢复”；
- 取消前有二次确认，取消后仍保留任务和全部历史；
- 恢复只把任务放回 `todo`，不删除取消历史；
- 取消和恢复分别写入 `canceled`、`restored` 历史；
- “恢复任务”是从取消状态恢复，与 M2-006 的“从回收站恢复”是两个独立用例。

今日摘要现在把取消任务单独显示：取消任务不进入完成数量分母，也不计入计划分钟；恢复后重新计入。

### 可读变化历史

任务详情按“最新在前”显示：

- 创建任务；
- 编辑标题、说明、科目、预计时长或优先级；
- 原日期、新日期和延期原因；
- 开始、完成、重新打开、取消和恢复；
- 按工作区 IANA 时区格式化的发生时间。

SQLite 中的 `before_json` 和 `after_json` 只作为内部不可变存储格式。Repository 读取后会完成以下处理：

1. 校验变化 ID、任务 ID、变化类型、时间戳和原因；
2. 反序列化并校验标题、说明、日期、科目 ID、时长、优先级、状态和完成时间约束；
3. 转换为 Rust `TaskChangeSnapshot`；
4. Command 只返回明确的 `before` / `after` 字段。

前端不会收到 `beforeJson`、`afterJson`、任务所属工作区、SQLite 行号、数据库路径、SQL 或原始内部错误。

## Command 边界

新增受控 Command：

- `reschedule_task(taskId, { plannedDate, reason })`；
- `list_task_changes(taskId)`。

`reschedule_task` 使用 `deny_unknown_fields`，不能在延期请求中夹带标题、科目、状态或其他字段。`transition_task` 新增固定令牌 `cancel` 和 `restore`，仍不接受前端自定义目标状态。

本工作项继续使用 schema v3，不新增迁移，也不提前实现拆分、回收站或学习记录。

## 维护者 Release Smoke

以下步骤由维护者手动操作，自动代理不会点击或控制桌面。

1. 完全关闭所有旧 KyStudy 窗口；
2. 启动本页记录的隔离 Release EXE，确认窗口正常启动；
3. 确认运行状态为“本地核心已连接”，Schema 仍显示 `v3`；
4. 切换到今天，记录当前“完成 / 有效任务数”“计划时长”和“已取消”三个摘要值；
5. 新建普通任务“M2-005 延期测试”，预计 `50` 分钟；
6. 打开该任务详情，确认“变化历史”出现“创建任务”，并显示今天的计划日期和本地发生时间；
7. 把标题改为“M2-005 计划变化测试”并保存；确认历史顶部出现“编辑任务详情”，显示标题从旧值变为新值；
8. 点击“开始学习”，确认状态变为“学习中”，历史顶部出现“开始学习”；
9. 点击“取消任务”，确认先出现“取消后仍可恢复”的二次确认；点击“返回”应不改变状态；
10. 再次取消并点击“确认取消”，确认状态变为“已取消”，列表以文字和 `×` 明确显示取消状态；
11. 确认今日“已取消”增加 1，有效任务分母减少 1，计划时长比取消前减少 `50` 分钟；
12. 打开取消任务详情，确认延期区域提示“已取消任务需要先恢复”，日期和原因输入不可用；
13. 点击“恢复任务”，确认回到“待开始”；摘要中的已取消数量、有效任务分母和 `50` 分钟计划时长恢复；历史依次保留“恢复任务”和“取消任务”；
14. 点击“标记完成”，确认延期区域提示“已完成任务需要先重新打开”，不能直接延期；
15. 点击“重新打开”，确认任务回到“待开始”，历史保留完成和重新打开；
16. 在延期区域选择与当前不同的日期，但暂不填写原因，确认“确认延期”不可点击；
17. 填写原因“先完成前置章节”但不提交，点击详情“关闭”；确认出现详情或延期区域未保存提示，选择“继续编辑”；
18. 点击“确认延期”，确认任务从今天列表移除，并出现“任务已调整到 YYYY-MM-DD，原日期已保留在历史中”的提示；
19. 使用日期选择器切换到刚才的新日期，确认“M2-005 计划变化测试”存在，标题、预计时长和状态没有被延期操作改写；
20. 打开任务详情，确认历史最新一项是“调整计划日期”，明确显示“今天 → 新日期”和原因“先完成前置章节”；
21. 检查历史仍按新到旧保留重新打开、完成、恢复、取消、开始、编辑和创建记录；
22. 在延期区域保留当前同一日期，即使填写原因，“确认延期”也应保持不可点击；
23. 关闭并重新启动同一个隔离 Release EXE，再切换到新日期；确认任务日期、状态和完整历史仍存在；
24. 确认界面没有显示 `beforeJson`、`afterJson`、数据库路径、SQL、storage key 或原始内部错误。
