# R45 周期计划缩量完整性验收

## 1. 问题与目标

编辑周期计划并减少总量时，不能删除已经完成的事项。判断依据必须是完成事项的序号是否仍落在新总量范围内，而不是只比较“已完成数量”。例如，仅第 10 项已完成时，将总量从 20 改为 5 也必须拒绝保存。

后端使用稳定错误码 `CYCLE_PLAN_COMPLETED_CONFLICT` 表示该完整性冲突。前端规范文案为：

- 提示：`已有完成事项的序号超出新的总量。`
- 操作建议：`请增大总量，保留所有已完成事项后再保存。`

## 2. 行为边界

- 完成事项的序号全部不超过新总量时，允许按既有规则缩量和重新排程；
- 任一完成事项的序号超过新总量时，整个保存事务失败，不删除完成历史，不写入部分计划或排程；
- 前端不根据当前 dashboard 自行判定能否缩量，后端持久化层是完整性的唯一权威；
- 保存失败后编辑窗口保持打开，并保留用户填写的总量及其他编辑值，便于直接增大总量后重试；
- 冲突提示不声称“完成数量过多”，避免在完成事项序号不连续时误导用户；
- 新建计划没有既有完成历史，不触发该冲突；归档、顺延、事项完成撤销等行为不属于本批次范围。

## 3. 前端实现与检查证据

- `cyclePlanClient` 对实际稳定码 `CYCLE_PLAN_COMPLETED_CONFLICT` 提供序号冲突的规范文案与调整建议；
- `CyclePlanPanel` 保存失败时只设置规范化错误；只有保存成功才关闭编辑窗口，受控 `draft` 不会因失败被替换或重建；
- 未增加客户端权威校验，避免并发窗口或过期 dashboard 绕过后端完整性保护。

## 4. 交叉审查闭环

- active/workspace 校验在同一事务内完成：保存只允许修改当前工作区中的未归档计划，避免校验与写入之间出现状态漂移；
- upsert 必须影响恰好一行；计划不存在、属于其他工作区或已归档时，不能继续写入事项；
- 稀疏完成集合 `{2, 5}` 已覆盖：缩至 `4` 必须报 `CYCLE_PLAN_COMPLETED_CONFLICT`，缩至 `5` 合法，并保留完成事项；
- 归档计划保存失败时验证为零写入，不修改计划或事项；
- 缩量冲突发生时不消费、不删除已有 shift undo token，失败的保存不会破坏仍有效的撤销能力；
- Rust 安全错误 DTO 与 TypeScript `ERROR_COPY` 对 `CYCLE_PLAN_COMPLETED_CONFLICT` 使用一致文案：`已有完成事项的序号超出新的总量。` / `请增大总量，保留所有已完成事项后再保存。`。
